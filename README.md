# VELLIUM

Тёмный лендинг и первая версия личного облачного дневника питания. Приложение рассчитано на русский интерфейс и мобильный экран.

## Запуск

```powershell
npm install --silent
Copy-Item .env.example .env.local
# Укажите URL и publishable key проекта Supabase VELLIUM
npm run dev --silent
```

Лендинг открывается на `/`, дневник — на `/app`.

Публичная версия: [ssskkkiiieee.bond](https://ssskkkiiieee.bond/). Адрес `www.ssskkkiiieee.bond` обслуживает ту же сборку.

## Что работает сейчас

- Личный профиль взрослого пользователя и ориентир энергии/БЖУ по формуле Миффлина — Сан Жеора с ручной настройкой калорий.
- Ручной ввод блюда с пересчётом пищевой ценности с 100 г на указанную порцию.
- Дневной баланс, история за последние семь дней, удаление записи.
- Идея следующего блюда из небольшого локального списка после первой записи. Подсказка ориентируется на остаток калорий и белка, не выдаётся за медицинский совет.
- Регистрация и вход через Supabase Auth; сохранение личного профиля и блюд в Supabase (Франкфурт).
- Экспорт профилей и записей в JSON, удаление всех профилей и записей из облака.
- Несколько взрослых профилей в одном аккаунте: отдельный дневник для каждого и общий экспорт семейных данных.
- Поиск упакованного продукта по EAN/UPC/GS1 GTIN в Open Food Facts; фото штрихкода распознаётся в браузерах с Barcode Detection API, при отсутствии поддержки код можно ввести вручную. Данные каталога проверяются перед записью.
- Недельный график выбранного профиля и установочный PWA-манифест. Офлайн-кэш содержит только оболочку и статические файлы; облачный дневник требует подключения.

Профиль и записи хранятся в проекте Supabase VELLIUM во Франкфурте. В браузере библиотека Supabase сохраняет сессию входа. Публичный `/api/*` проходит через Cloudflare Tunnel к API на VPS (`127.0.0.1:8300`); статика обслуживается Nginx (`127.0.0.1:8310`). Фото проходит сжатие и удаление метаданных, оценка показывается для проверки и попадает в дневник только после подтверждения. Gemini обрабатывает отправленные фото, аудио и описание как внешний сервис; настройка хранения в Supabase во Франкфурте не означает, что обработка Gemini происходит там. Детские профили и совместный доступ разных аккаунтов пока не включены.

Для локального API создайте виртуальное окружение в `backend/.venv`, установите `backend/requirements.txt`, задайте на сервере `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `GEMINI_API_KEY`, `GEMINI_MODEL` и запустите `uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000`. При проверке 19 октября 2026 года модель `gemini-3.5-flash-lite` обработала фото; доступность модели проверяйте для своего ключа. Во фронтенде задайте `VITE_API_URL=http://127.0.0.1:8000`. Ключ Gemini не должен попадать в переменные `VITE_*` или клиентский код. Для публичного сервера ограничьте размер тела запроса до 5 МБ на прокси и используйте общее хранилище лимитов при нескольких процессах API.

Отдельный проект Supabase VELLIUM (`jabznldqaeqtgtczulwa`, Франкфурт) содержит таблицы `nutrition_profiles` и `meal_entries`. Схема находится в [миграции](supabase/migrations/20261019000100_personal_nutrition_core.sql): обе таблицы защищены RLS, записи блюд дополнительно ограничены связным ключом на профиль того же владельца. Доступ двух синтетических пользователей проверен в откатываемой транзакции; после неё таблицы и тестовые аккаунты пусты. В Supabase Auth установлены Site URL и два Redirect URL для публичных адресов, а также включён SMTP Resend с ключом, ограниченным отправкой с домена VELLIUM. Доставку письма до реального почтового ящика и полный цикл регистрации ещё нужно проверить; резервное копирование также требует настройки.

Продакшен-сборка создаётся с `VITE_API_URL=''`, чтобы запросы шли на текущий домен. Конфигурации Nginx и туннеля находятся в `deploy/`. Секретный токен туннеля хранится только на VPS в `/etc/cloudflared/vellium.token`; локальные файлы с ключами не входят в Git.

## Следующие этапы

1. Проверка доставки подтверждения и полного цикла Auth/дневника на двух подтверждённых тестовых аккаунтах.
2. Проверка полного голосового сценария в браузере и согласование доступной модели Gemini для продакшена.
3. Проверка сканера на реальных телефонах и дополнительный способ распознавания для браузеров без Barcode Detection API.
4. Детские профили и совместный доступ семьи, расширенная аналитика, Excel и доступность на реальных устройствах.
5. Проверка полного сценария на публичном домене и резервного копирования без вмешательства в действующие VPN-сервисы.

Публичный сервис в России требует отдельной юридической проверки трансграничной обработки и локализации персональных данных. Пользователь выбрал Франкфурт для хранения данных; это техническая настройка, а не заключение о соответствии 152‑ФЗ. Сайт опубликован, но соответствие требованиям для обработки данных реальных пользователей пока не подтверждено.
